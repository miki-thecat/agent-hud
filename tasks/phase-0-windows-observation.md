# Phase 0 — native Windows Codex observation spike

Status: READY FOR CODEX

## Goal / why

Determine, on the actual Windows machine and currently installed Codex Desktop version, whether `agent-hud` can obtain trustworthy live session state from Codex Desktop without taking ownership of threads or interfering with approvals/user-input requests.

This task exists to eliminate the largest technical uncertainty before substantial UI implementation.

## Current -> desired behavior

### Current

The repository has an intended native Windows HUD architecture, but the exact supported observation path into the Desktop-owned Codex app-server is not proven.

Current upstream evidence indicates that native Windows may not expose a supported second-client control socket/listener at all.

### Desired

Produce a small, reproducible diagnostic spike and evidence report that answers:

1. Can an external read-only process attach to the same live Codex state used by Codex Desktop?
2. Can Desktop-created sessions be discovered with authoritative live status?
3. Can `waitingOnApproval` / `waitingOnUserInput` be observed safely?
4. If not, what is the strongest trustworthy read-only signal available without UI scraping or invasive process tricks?

The result may legitimately be `BLOCKED_SUPPORTED_LIVE_PATH`. That is a successful Phase-0 outcome if demonstrated with evidence.

## Scope

### In scope

- inspect installed Codex Desktop/CLI/runtime versions,
- inspect safe process metadata and local endpoint topology,
- detect whether Codex Desktop exposes a supported app-server endpoint,
- start a separate `codex app-server` child over its documented transport when useful,
- perform the documented initialize handshake,
- issue read-only discovery calls such as `thread/list`, `thread/loaded/list`, and `thread/read` without resuming threads,
- normalize enough response data to print a diagnostic table,
- compare results while known Desktop sessions are idle, active, and waiting for input/approval when that state can be created naturally by the user,
- inspect persisted metadata schema only as needed to establish the claim ceiling,
- record side effects and final verdict,
- add deterministic fixtures/unit tests for any parser/reducer logic created by the spike.

### Out of scope

- production HUD UI,
- native rendering stack,
- notification system,
- Git/GitHub integration,
- orchestrating Codex sessions,
- answering approvals/user-input,
- resuming Desktop-owned threads,
- starting/steering/interrupting turns,
- process injection/debugger attachment,
- memory scraping,
- stealing/duplicating inherited stdio handles,
- screen/UI scraping,
- modifying Codex Desktop binaries/configuration to force an endpoint,
- treating timestamps or process existence as authoritative liveness without explicit proof.

## Material constraints

### Read-only / passive

Codex Desktop remains the sole interactive owner.

The spike must not knowingly send any request that can mutate a Desktop-owned thread or resolve an actionable request.

### Truthfulness

Never map weak evidence to a stronger product state.

Examples:

- recent mtime != `WORKING`,
- process exists != thread active,
- persisted latest message != `DONE`,
- absent recent writes != `IDLE`.

If the source cannot prove a state, report `UNKNOWN`.

### Performance

Performance is not the main risk in Phase 0, but avoid high-frequency polling or whole-machine scans. Diagnostic polling, if used, must be bounded and temporary.

### Privacy

Do not print or commit:

- auth tokens,
- API keys,
- full private prompts/messages unless explicitly needed for a local one-off test and kept out of committed evidence,
- unrelated personal filesystem data.

Prefer IDs, coarse status, paths limited to the test repository, and redacted snippets.

## Reuse / existing path

Prefer:

1. documented Codex app-server protocol,
2. schemas generated by the locally installed Codex version when useful,
3. standard Windows process/listener inspection,
4. thin custom diagnostic code.

Use `morgadoronan/codex-agents` and `pingdotgg/t3code` for ideas about protocol normalization and passive safety, but do not copy their broader architecture into the spike.

## Design notes

### Suggested spike shape

Keep the executable intentionally small.

Conceptually:

```text
phase0_probe
  |
  +-- environment/version probe
  |
  +-- Desktop topology probe
  |     - processes
  |     - command line
  |     - supported control endpoint presence
  |
  +-- independent app-server probe
  |     - spawn child
  |     - initialize
  |     - thread/list
  |     - thread/loaded/list if supported
  |     - optional thread/read (no resume)
  |
  +-- evidence formatter
```

Do not build the production adapter abstraction until the observation topology is known. Small parser modules are fine if they improve tests.

### Preferred language

Rust, because the production application is intended to be Rust and protocol parsing code may be reusable later.

However, do not add the Windows graphics dependencies in this spike.

### Dependency policy

Use the minimum practical dependencies. `serde` / `serde_json` are justified. Add process/transport libraries only when the standard library cannot cleanly handle the documented path.

Do not add Tokio merely by habit. If an async dependency materially simplifies a required documented transport, explain why in the completion report.

## Local evidence procedure

The implementation should make the following procedure straightforward.

### 1. Baseline environment

Capture non-secret outputs equivalent to:

```powershell
codex --version
codex app-server --help
codex doctor
```

Record Codex Desktop version separately if CLI cannot report it.

### 2. Inspect Desktop-owned Codex processes

Use a safe Windows query such as:

```powershell
Get-CimInstance Win32_Process |
  Where-Object { $_.Name -ieq 'codex.exe' } |
  Select-Object ProcessId, ParentProcessId, CommandLine
```

Do not assume the exact installation path.

### 3. Inspect supported endpoint evidence

Check, without mutating anything:

- whether `$HOME\.codex\app-server-control\app-server-control.sock` exists,
- whether relevant Codex PIDs own listening TCP endpoints,
- whether a clearly documented Codex named pipe/control endpoint exists,
- `codex doctor` app-server/daemon status.

Do not infer a private endpoint merely from an unrelated pipe name.

### 4. Independent app-server read-only probe

Start a separate documented app-server child if safe and supported.

Perform only:

- `initialize`,
- `initialized`,
- `thread/list`,
- `thread/loaded/list` when available,
- `thread/read` only if needed and without resume.

Compare Desktop-created known sessions.

Expected current hypothesis: a separate server can see persisted threads but cannot see Desktop-owned live liveness, so Desktop threads may appear `notLoaded` there.

Treat the hypothesis as falsifiable; do not hard-code it as the result.

### 5. Controlled state comparison

With user-observable Desktop sessions, collect probe results for the applicable states:

- Desktop thread open but idle,
- Desktop thread actively running,
- Desktop thread naturally waiting for approval/user input,
- Desktop thread completed.

Never create these states by sending mutating protocol requests from the probe.

### 6. Persisted-state claim ceiling

If live attachment is unavailable, inspect only enough local schema/metadata to determine whether authoritative liveness exists outside the Desktop-owned server.

If it does not, document that fact. Do not build heuristic production state as part of this task.

## Acceptance criteria

- [ ] AC-01: The spike reports the actual Windows version, Codex Desktop/runtime version where obtainable, and CLI version without exposing secrets.
- [ ] AC-02: The spike establishes whether native Codex Desktop exposes a supported external control endpoint on the tested installation.
- [ ] AC-03: A separate documented app-server connection can be initialized and queried read-only, or the exact supported-path failure is recorded.
- [ ] AC-04: At least one Desktop-created thread is compared against the external probe while its Desktop state is known.
- [ ] AC-05: The result distinguishes persisted discoverability from authoritative live status.
- [ ] AC-06: No Desktop-owned thread is resumed, started, steered, interrupted, or answered by the probe.
- [ ] AC-07: No auth token/key or unrelated private prompt content is committed to the repository.
- [ ] AC-08: The final verdict is one of the explicit states below and includes evidence plus a claim ceiling.
- [ ] AC-09: Any reusable protocol normalization logic has deterministic tests/fixtures.
- [ ] AC-10: The spike records whether it caused any observable change, duplicate request, lock conflict, crash, or Desktop degradation.

## Verdict states

Use exactly one primary verdict:

### `SUPPORTED_LIVE_READONLY`

A supported local path exposes the required authoritative live state while Desktop remains owner, with no observed interference.

### `SUPPORTED_COARSE_ONLY`

A supported local path exposes trustworthy coarse live state but not all desired activity/message/input details.

### `UNSAFE_DUPLICATED_REQUESTS`

A candidate observer path duplicates or competes for actionable requests or otherwise risks changing Desktop behavior.

### `BLOCKED_SUPPORTED_LIVE_PATH`

No supported native-Windows path reaches authoritative Desktop-owned live state on the tested version.

### `INCONCLUSIVE_ENVIRONMENT`

The machine/setup prevented a trustworthy conclusion. State exactly what is missing.

## Stop / escalation conditions

Stop rather than improvise if:

- the only apparent path requires debugger/process injection or handle theft,
- a read-only observer unexpectedly receives an actionable request and safe semantics are unclear,
- a test would require answering/interrupting/resuming a Desktop-owned thread,
- the discovered endpoint is undocumented/private and its ownership semantics cannot be established,
- testing risks corrupting current Codex sessions,
- Codex protocol/version behavior conflicts materially with the repository's current assumptions.

## Completion report

Report only:

- primary verdict,
- exact tested Codex/Windows versions,
- supported endpoint/topology discovered,
- live states actually proven,
- checks run and results,
- any interference observed,
- files changed,
- next recommended bounded task.

Do not claim the production HUD is feasible until `SUPPORTED_LIVE_READONLY` or an explicitly accepted reduced product contract is established.
